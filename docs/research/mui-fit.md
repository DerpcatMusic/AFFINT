## Decision

**Use the owner's MUI for AFFINT's initial native shell, with an AFFINT-owned winit/wgpu host and an independent document renderer. Keep egui as the named fallback, not as a second shell implemented in parallel.**

This changes the earlier report's UI recommendation because that report had not examined MUI. The decisive new evidence is a standalone native host plus public, same-device GPU interfaces—not a claim that MUI is faster. MUI supplies intrinsic typed layout, hit geometry, ordinary controls, editable UI fields, focus, IME handoff, accessible semantics, and repaint deadlines. Vello Hybrid 0.2.0 supplies externally owned texture bindings and ordered texture-rectangle draws. AFFINT can use these without a Linux toolkit fork or routine GPU readback. [M1–M7, V1]

MUI fits the owner's preference and permits deliberately compact, Affinity-style chrome without adopting vendor assets. Its typed intrinsic row/column/grid/pin layout and shared paint/hit geometry are a good fit for toolbars, inspector panels and canvas overlays. Eframe/egui remains the lower-risk ready-made host: it already provides shared GPU state and a custom callback, and avoids writing as much native lifecycle/clipboard plumbing. MUI earns the recommendation here because its required GPU seam is public and the missing first-workflow host logic is bounded, not because those costs disappear. It is not a ready-made publishing/photo editor, and its plugin origins do not establish production desktop parity. Native clipboard, command scopes, modal behavior, menus, docking, file dialogs, recovery, and full editor accessibility require application work. Missing application-specific widgets alone do not justify rejecting it: egui also needs AFFINT-specific workflows, styling and panel organization.

**Do not select MUI's RGBA8 image-fill/effect pipeline as AFFINT's full-float photo compositor.** Keep original assets, f32 linear-premultiplied evaluation, masks, live operations, requested-resolution export, transactions, and history outside the toolkit. The UI choice does not weaken `docs/render-contract.md`. [M4, M5, V1]

The root coordinator should implement the bounded single-device proof below before expanding the shell. If that proof exposes an unfixable public-interface limitation, requires a general toolkit fork, or cannot preserve the declared display/ordering contract, use the already-researched eframe/egui 0.36.2 route. This is a normal implementation acceptance gate, not an undecided toolkit comparison.

## Native host: real code, application-owned lifecycle

`crates/mui-preview/src/main.rs:715–953` implements winit `ApplicationHandler`, AccessKit user events, resumed/window creation, window input and deadline-driven waiting. `host.rs:53–75` and `host_gpu.rs:74–103` create a wgpu instance with the owned display handle, a safe window surface, and GPU state. `device.rs:22–53` chooses a surface-compatible adapter, requests device/queue, records adapter information, and registers a device-lost flag. This is a standalone native path, not just a browser canvas or plugin-parent-window sample. [M1]

Device ownership is explicit:

- `OnDevice<T>` owns public device/queue fields and device-local state.
- The plain host constructs `vello_hybrid::Renderer`, `Resources`, MUI `Cache`, and `Scene` on that device. `begin()` returns `mui::vello::Gpu` borrowing them, with an `Atlas` borrowing the same device/queue. [M1, M4]
- `HybridEffects::new` takes device/queue references and clones the handles; it does not secretly create an independent GPU device. Its fields are private and its high-level interface specializes in MUI effects. [M5]
- Surface loss recreation exists in the effects host; device loss rebuilds the entire device-local state through `OnDevice::recover`. The plain host still reports surface loss as “restart the gallery.” No AFFINT recovery policy should be copied from that gallery shortcut. [M1]

The host is useful reference code, **not production AFFINT lifecycle code**. Gallery startup uses `expect`, close exits without document policy, and device creation/recovery use blocking calls. AFFINT must use structured failures, atomic dirty-document close/save policy, worker completion wakeups, explicit adapter/format limits, zero-size handling, and bounded recovery. No slow decode, save/export, or imaging work belongs inside `Ui::frame` or window painting.

X11/Wayland source wiring is present. This worker did not launch either backend, exercise an IME, test a clipboard/portal, suspend a GPU, or verify macOS/Windows behavior. Portability is credible infrastructure, not tested product support.

## GPU seam and least-invasive integration

### What the public interfaces actually provide

`mui::scene::canvas` is a callback returning path-based `Draw` values. It is **not an arbitrary wgpu render-pass callback**. `Draw` carries path/fill/stroke/hit tags; `CanvasCache<K>` caches the draw list when key and size agree. `.float()` is paint/hit ordering, not a GPU surface. [M3]

`Fill::Image` takes immutable `Arc<[u8]>` straight RGBA8 CPU bytes. `Gpu::image` premultiplies them, uploads once to Hybrid's private atlas, and keys residency by buffer identity. It does not accept an arbitrary external GPU texture. Atlas capacity and invalid-image refusal become a **solid stand-in**, not a structured frame failure. This path is reasonable only for bounded, explicitly validated chrome imagery—not for exact document output. [M4]

The useful lower seam is public:

- `mui::vello::Gpu { scene, resources, cache, atlas }` exposes its borrowed Hybrid `Scene` and resources.
- `mui::vello::Canvas` exposes transforms, clips, blend layers and normal UI painting.
- `mui::vello::paint(&mut impl Canvas, &ResolvedScene, Affine)` appends the chrome walk. Its `begin_frame` implementation ticks the cache; **it does not reset the Hybrid scene**, so preceding native texture draws remain. [M4]
- `vello_hybrid::Scene::draw_texture_rects(TextureId, ImageQuality, rects)` appends samples at the current scene position. Each `SampleRect` contains a `RectU16` source region and an affine mapping composed with the current scene transform. Existing scene clip/blend state applies. [V1]
- `TextureBindings::insert(TextureId, TextureView)` supplies externally owned views at render time. Required binding: non-multisampled, non-array 2D, float-sampleable, mip 0, with `TEXTURE_BINDING`. No image-atlas upload or host readback is performed by this binding interface. Missing bindings return `RenderError::MissingTextureBinding`. [V1]
- `Renderer::render(scene, resources, device, queue, encoder, RenderSize, target_view, bindings)` records UI rendering on the caller's encoder/device. It **clears the target to transparent**, so one must not draw the photo directly into the surface and then expect this renderer to preserve it. [V1]

MUI's `Layer::External` and `HybridEffects`/`TiledEffects` are currently **external welded-material** machinery, not a generic application texture/custom-pass registry. `paint` explicitly refuses such external scenes; `HybridEffects` translates their `ExternalWeld` entries to texture draws in the proper paint slot. `render_with_overlay` runs after the complete UI walk and is intended for debug overlays. Putting a photograph there would paint over menus/tooltips. [M4, M5]

### Recommended first host: display texture first, transparent chrome above

This needs an AFFINT host, **not a change to MUI**:

1. The host creates one compatible wgpu 29 device/queue. The document renderer receives those handles at its real GPU seam; it owns resident source/intermediate tiles, revision identity, precision policy and retirement. MUI objects stay in the shell, not in the document or worker-render interface.
2. Evaluate photo/vector/mask operations in AFFINT's declared linear-premultiplied float pipeline. Preserve full-resolution assets and exact export. A viewport texture is a display product; it must never become the source for exact rendering or saving.
3. An independent display shader samples the completed float result and writes a **viewport-sized RGBA8 non-sRGB UNORM display texture** on that device. Only here apply the working-to-display transform and declared display range policy. For translucent output, unpremultiply before nonlinear color conversion and premultiply afterward; alpha-zero handling must be defined. The simplest proof composites the canvas backdrop in linear light and emits an opaque display texture. Never apply an sRGB transfer directly to linear-premultiplied RGB and call that correct.
4. Build the intrinsic MUI layout with a named, rectangular document viewport and transparent root/viewport fills. Panels have explicit backgrounds. Artboard/checkerboard painting belongs beneath the document, not in an opaque MUI root that will cover it. Use that viewport's resolved logical frame to determine physical extent and placement; use MUI's hit surface for tool routing and app geometry for document hit testing.
5. Reset the host's Hybrid scene once. Encode the document sample with an identity scene transform and a physical-pixel viewport clip. `SampleRect::transform` maps the display texture's pixel extent to the snapped physical viewport position/extent. Pop that clip, bind the view under a stable host-owned `TextureId`, and then call `mui::vello::paint(..., Affine::scale(device_scale))` for logical-unit chrome, canvas selection/handle paths and floated popups. This avoids scaling an already physical-sized display texture twice. **All chrome is above the one central document surface.** This is the required order for the initial editor; it is not a claim of arbitrary native-pass placement in any subtree.
6. Record the independent display pass before Hybrid `Renderer::render` in compatible queue order. Submit, notify winit before present, and present once. Keep texture/view/binding identities alive through every referencing submission. On resize/device loss, rebuild device-local resources and discard stale texture tickets. A bound view is not proof that its producer can overwrite or recycle it at any time.
7. Retain the host's renderer/resources/MUI cache and reusable encoding. Changing only display-texture contents need not reconstruct a static draw description. When the UI paint list, viewport transform/extent, ordering, font/image identity or binding topology changes, invalidate the affected encoding. Skip settled frames in the host. Initially use simple whole-scene chrome retention rather than transplanting the welded-effects tile pool into the photo engine.

The recommendation deliberately pays a GPU display conversion pass; it does **not** pay GPU→CPU→GPU for ordinary edits. An initial CPU reference may upload its completed display pixels without any GPU readback. GPU reference comparisons/export/explicit analytics are named, separately budgeted exceptions.

A float-sampleable external texture is technically bindable to Hybrid, but Hybrid expects premultiplied values in the target color space and supplies no AFFINT ICC/linear-working conversion. Its RGBA8 layer textures and MUI's selected UI contract are not a full-float document compositor. Convert the display result deliberately rather than passing working floats through and hoping for faithful color. [V1, M5]

**Alternative when display requirements demand bypassing Hybrid's document sampling:** render transparent MUI chrome to a persistent RGBA8 texture, then use AFFINT's final display shader to combine the float document and that chrome into the surface. Hybrid's mandatory clear is harmless on the chrome target. This remains same-device and readback-free, but adds texture memory/bandwidth and requires a declared alpha/color policy. It is a bounded host alternative, not a second UI backend.

A future need for native document surfaces interleaved with arbitrary MUI subtrees would justify a small, explicit generic external-surface paint slot plus retained invalidation. That seam is **not presently supplied by `canvas` or the welded convenience renderer**. Do not pretend the first-under-chrome strategy solves nested opacity groups, arbitrary background/foreground interleaving, or every editor thumbnail surface. Such work is unnecessary for the first central-canvas proof.

## Input, editor UI and accessibility

### Present in source

- Buttons, toggles, sliders/knobs, text fields, custom tagged paths, scroll/clip containers, payload drag/drop, tooltip pinning and typed spacing/theme choices exist. Intrinsic layout is real resolution code, not README-only language: `resolve_scene_animated` calls cached layout with offered size and measurement callbacks, then constructs paint/hit surfaces. [M2–M4]
- Focusable surfaces participate in Tab/Shift-Tab scene order; disabled nodes are excluded. Clicking, semantic actions, and Escape change focus. Ordinary keyboard activation and semantic value actions are wired. [M2, M7]
- UI fields have one-line selection, grapheme stepping/deletion, copy/cut/paste requests, preedit underline and committed text insertion. Preedit does not change the value; its cursor byte range is checked before slicing. `Frame::ime` reports scene-unit caret bounds. The host enables IME and converts caret placement to physical coordinates. [M2, M6]
- `Frame::edits`/`Ui::edit` bracket gestures with `Begin`/`End`; they are not document transactions or undo history. Cancellation can also owe an `End`. AFFINT must distinguish host cancellation from successful commit and keep one continuous gesture atomic. [M2]
- Ordinary clips affect paint and hit paths. Floats are deferred and painted last, preserving authored parent identity while deliberately escaping ancestor clips. A popup over the viewport should use this behavior; document overlays that must remain inside the viewport must not be indiscriminately floated. [M3]
- `mui_access::tree_update` returns an AccessKit tree with stable keyed IDs, roles, values, disabled/focus state, text runs and selections. The preview initializes the winit adapter before showing the window, forwards events, publishes active updates, and dispatches accessibility actions through `Ui::request_action`. This is implemented plumbing, not an accessibility conformance claim. [M7]

### AFFINT-owned work and specific limitations

- **System clipboard:** the gallery stores a private `String`; `tick` supplies it as clipboard data each frame. This is not integration with the OS clipboard. The `Input` contract expects current clipboard contents because a paste arrived; implement asynchronous/current native clipboard handling and error reporting, not a stale internal buffer. [M1, M6]
- **Menus and commands:** the examined menu demo is a column of labels, not a native menubar, command model, mnemonic system or keyboard menu navigator. Build only working commands, command scopes, shortcuts, popup dismissal and focus restoration. `Ui::shortcuts` suppresses the entire global stream when a `Kind::TextInput` has focus; define exceptions such as Save at the host command layer, and keep text-edit keys from also triggering document undo. [M2, M6]
- **Modal dialogs and docking:** there is no complete docking manager or modal focus scope in the examined public UI interface. Tab cycles all enabled focusable surfaces. A modal must gate underlying hit/focus/command targets, trap/restore focus, and expose dialog semantics. Fixed compact panels and document tabs are a valid first workflow; resizable/detachable/persistent docking is app state, not a reason to invent fake controls. File pickers/portals and dirty-save prompts are native host responsibilities, with no blocking I/O in painting. [M2, M3, M7]
- **Accessibility role coverage:** MUI `Kind` covers Button, Slider, Toggle, one-line TextInput, Label, Group and Scroll. It does not encode menu/menuitem/dialog/tab/tree semantics. Augment the returned AccessKit tree for AFFINT's app-level roles or make a narrow audited extension; also handle semantic actions and focus policy. Labelling everything Group/Button would not be a faithful accessible Layers tree or menu. The bridge currently marks text runs left-to-right and counts characters rather than grapheme clusters; verify RTL/complex-script navigation rather than assuming visual shaping proves accessible navigation. [M3, M7]
- **UI text is not document typography:** the field is single-line and has no complete rich-text/multiline/layout-editor interface. Source comments identify imperfect pointer placement during composition and hidden selection while composing. The document engine still needs its independently chosen fonts, shaping, paragraph/layout and persisted style policies. [M6, E1]
- **Raw painting input:** `PointerInput` contains one position, three supported gesture buttons and modifiers. It does not carry pressure, tilt, multiple pointer IDs or touch contacts. The gallery ignores unsupported mouse buttons/touch events. Stylus/raw tool input must have its own host→tool interface; the chosen winit/platform capabilities need a separate audit before promising professional tablet support. A UI pointer abstraction must not discard required document tool samples. [M1, M6]
- **Scaling:** pointer/offered dimensions and IME placement are explicitly scaled. However, the gallery passes winit `PixelDelta` wheel values into `Input::wheel` without division by scale, although `Input::wheel` is documented in scene units. This is a source-level DPI inconsistency to fix/test in AFFINT's host. Scale-factor changes, pointer capture outside the window, multiple monitors, close/suspend/recovery and multiple windows need real platform proofs. [M1, M6]

These are concrete application/integration costs. They are not assertions that Affinity lacks a feature, and they are not evidence that egui automatically supplies every missing editor workflow.

## Incremental behavior, idle and resource risks

MUI is immediate tree construction with retained caches, not a complete fine-grained reactive editor engine. Each normal `Ui::frame` follows identities, updates input/springs, resolves the tree, walks scene/geometry, allocates a fresh paint/surface description and settles interaction. Layout measurement, text/outlines/borders and hit geometry can be reused; equal measurement keys do not eliminate the complete tree walk. `Ui::set_text` can change a reserved readout without full layout resolution, and `canvas_cached` can reuse local path lists when every semantic input is in its key. Neither API is a document cache or permission to omit an invalidation input. [M2, M3]

Idle is host-driven. `Frame::animating` requests another frame for moving interaction/springs; `repaint_after` supplies tooltip/caret deadlines. The preview uses `ControlFlow::Wait` or `WaitUntil` and hidden-window gating. A settled UI with no focused caret/deadline can stop asking for frames. A focused caret intentionally wakes periodically; theme live-reload adds a 500 ms poll when configured. Processing queued pointer events can resolve several UI frames before one presentation; coalescing must preserve press/release, text and gesture edges. [M1, M2]

`HybridEffects` reuses equal paint/transform/mapping encoding; an unchanged frame into the identical previously presented view can record no render. A freshly acquired swapchain view defeats that particular same-view shortcut. `TiledEffects` has damage-tracked 256-pixel tiles, guards, separate memory admission, and an adaptive full-window path for widespread damage. The host must opt into and retain it. These are real chrome optimizations but not proof of float photo tiles or total application memory limits. [M5]

Risks that need explicit policy:

1. **Silent chrome-image substitution:** atlas-full/malformed/oversized images can become stand-ins; exact artwork never goes through this path. Prevalidate small chrome assets and surface diagnostics, or avoid image fills in the first proof. [M4]
2. **Atlas allocator mirror:** MUI mirrors Hybrid's private image allocator to avoid upstream allocation `unwrap`. Matching atlas settings and disabled glyph-atlas caching are necessary. Changing renderer settings without `Cache::for_atlas`, or casually enabling glyph atlases, breaks the assumption. [M4]
3. **Lifetime accounting:** image entries use Weak buffer identity and sweep at subsequent image lookups, not an unconditional global byte-cap pass. Fonts unused for 64 paint walks age out at this pin. These policies are not complete live/queued GPU-residency accounting; account for original assets, workers, cache, staging and retired submissions separately. [M4]
4. **Color/format assumptions:** high-level effects accept only non-sRGB RGBA8/BGRA8 UNORM. The plain host prefers a non-sRGB sibling but can fall back to an sRGB surface; copying that fallback would contradict the stated encoding policy. Use explicit supported-format failure or the independently verified final shader. The old `NATIVE-GPU.md` prose also says fonts remain forever and the plain host lacks device recovery; newer source shows font aging and `OnDevice` recovery. Source at the pin wins over stale prose. [M1, M4, M5]
5. **Blocking/error paths:** sample `expect` and synchronous initialization/recovery are not AFFINT error policy. Unsupported texture dimensions must be reported, not silently scaled down. Several gallery paths clamp window dimensions to u16/device limits; that must not leak into document exact-output policy. [M1, M5]
6. **Vector preparation cost:** Hybrid processes arbitrary UI paths on the CPU. Do not stream all document vectors through MUI's chrome tree or assume retained static controls make a dense changing vector document cheap. Keep the document rendering backend independently selectable and validate numerical/color fidelity. [B1]

No newly reproduced crash or measured regression is claimed. The observations above are source-visible constraints and risks; the wheel-unit mismatch is a concrete host inconsistency, still untested here.

## Existing performance evidence and its limits

**No MUI-vs-egui AFFINT benchmark exists in this research. No benchmark was run by this worker.** Choosing MUI neither proves higher responsiveness nor supports a synthetic speed score.

The persistent MUI report `docs/rendering-investigation.md` and raw logs record a Ryzen 7 7800X3D, physical RX 6600, RADV Vulkan, Linux 7.3.0-rc3 development desktop with other applications active. The headless fixture is 1280×800, five warm-up frames and **50 measured frames per case**, not a sustained editor session or a 60-second workload. The cited records do not establish an overall process watchdog/deadline; fixed frame counts are not a guaranteed elapsed-time limit. A cold case resets UI state, not the GPU device. Each frame waits for GPU completion; values are completion latency, not input-to-present latency/FPS. [B1]

For 96 curves × 50 cubic segments, all changing, three recorded run medians were 18.749/18.749/18.750 ms for cached Hybrid and 1.030/1.040/1.009 ms for classic compute. In run 1 their recorded p95 values were 18.799 and 1.607 ms. These equal-content synthetic results warn against using Hybrid as the dense document-vector renderer; pixel-level backend parity remained outstanding. They do not show that egui chrome is faster or slower. [B1]

The text fixture records 717 surfaces, 632 paint operations and 472 glyph runs. One static cached-Hybrid run is 6.251 ms median, 6.282 ms p95; classic is 6.001/7.034 ms. Process peak RSS was 161.6 MiB for that executable, not a toolkit-only memory figure. The vector run's 70.0 MiB RSS and classic's 8.7 MiB buffer estimate likewise are not complete physical VRAM accounting. Earlier experimental PathCache rows remain in historical logs even though the investigation says that cache was deleted. These are recorded earlier measurements embedded in the current pin, not a fresh reproduction of every number on this pin. [B1]

The adaptive-tile report uses the same desktop and fixed five-plus-fifty frame method. Its medians of three medians show text-cold 33.594→13.971 ms, text-static 2.503→2.541, one-knob 4.132→4.416, changing-vectors 28.847→18.571 and static-vectors 0.632→0.627. Sparse cases did not uniformly improve. The tile-only case always ran first; desktop scheduling was not isolated. This evidence supports workload-specific invalidation, not unconditional use of tiled rendering. [B2]

The earlier September 13 lab is **classic Vello 0.10 compute vs pinned GPUI**, not MUI Hybrid vs egui. It records RX 6600/RADV 26.2.2-arch3.2, Ryzen 7800X3D, dedicated rootful Xwayland, fixed 60-sample cases and longer three-process 300-sample cases with five warmups. Its presentation measurements excluded scene encoding and included CPU acquire/draw/present/device wait; Vello also paid an offscreen blit. Typography was absent. GPU clocks/power and desktop activity were not isolated. Its earlier GPUI gradient defect was subsequently corrected; do not reuse that historical defect as a current toolkit ranking. [B3]

`NATIVE-GPU.md` reports a running hardware effects path and bounded local effect budgets, but limits it to small analytic rounded-rectangle material effects. That is not a measured 24/48 MP full-float photo workflow, an ICC proof, a tablet proof, or weak-laptop validation. Its provisional/lost-log observations are not promoted to fresh evidence here. [B1–B3]

Run the built app in X11 and Wayland sessions. Inspect actual AccessKit roles/actions for controls and the app's dialog/menu/tab/Layer semantics; do not count adapter construction as screen-reader validation.
6. **Counters and bounded resources.** Record adapter/driver/backend, toolchain, output scale, image extent, upload/readback bytes, queue submissions, CPU resolve/encode and present timing, peak CPU/GPU budgeted bytes and dropped stale results. An idle unfocused window should show no continuous redraw/submission; focused caret deadlines are intentional. Pan/zoom and ordinary adjustments must not read back full image pixels. No 24/48 MP speed claim follows from this small proof.
7. **One coordinator verification cycle.** After the implementation and lock exist, from AFFINT run `python3 scripts/verify --label mui-proof-r2 --build-app --jobs 4`. This invokes format-check, tests, Clippy and the app build under the repository's exclusive lock. Tests should include cached/uncached invalidation and CPU/GPU/display tolerances, not only a screenshot or a self-roundtrip. Launch the already-built `./target/debug/affint-app` for platform proof; no parallel `cargo run` is needed. The existing verification script does not itself supply interactive platform evidence.

Acceptance is a working public-seam native editor slice with honest errors and independent exact rendering—not the complete product. Reject this direction only for a demonstrated required seam/fidelity/maintenance failure. If falling back, adopt the prior egui family consistently (0.36.2 / wgpu 30.0.1), preserve the document/renderer interfaces, and do not hide a second GPU device or a readback bridge behind “compatibility.”
